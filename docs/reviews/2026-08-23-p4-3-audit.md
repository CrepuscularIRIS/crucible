## §0 前提变更：`bypassPermissions` 作为唯一生产模式的后果

接受这个前提，等于承认**每次工具调用都没有人在环**。于是全部约束落到四道结构性控制上：

| # | 结构性控制 | 实现位置 | 本次是否被穿透 |
|---|---|---|---|
| C1 | journal 只追加 + 防篡改 | `state.ts` `assertJournalIntact` | **是**（§2.1，从账本外穿透） |
| C2 | `probe_run` 只在 bwrap 内执行 | `sandbox.ts` | 否（§1.2 已复算） |
| C3 | `research_kit` 只读、kernel 无写路径 | `research_kit/__init__.py` | **是**（§3.3，实际走的不是它） |
| C4 | declare 时三道内嵌 gate | `server.ts` `report_declare` | 否，但对 §2.1 结构性不可见 |

三条推论，都由前提直接得出：

1. **穿透 C1–C4 的问题一律升级为阻断项。** 没有权限询问兜底，结构性控制就是**唯一**控制。
   §2.3（子代理继承可写 MCP）在有询问的世界里是"重要不阻断"，在这个前提下是阻断项。
2. **`plan` 模式的缺陷降级但不注销。** 它不是生产路径，但 UI 仍然提供它，用户仍会选它，
   它仍然在"只读规划"的名义下执行 shell 命令（§3.1）。
3. **失效的权限机件必须删除或显式标注。** `createCanUseTool` 整套询问机件在生产中不可达
   （§5.1），留着它等于代码库持续宣称一道并不存在的控制——这正是 §5 要治的病。

## §2 阻断项

### 2.1 预登记被账本外的观测击穿，且任何 gate 都看不见

**现象**：FRICTION 记录父 Agent 在预登记前用 Bash 跑了两次 `bun test packages/research-mcp` 预览结果。

**实证**（不依赖该记录，产物本身自证）：

- `run.init` 08:42:52.461 → `claim.propose H1` 08:43:40.788，间隔 **48 秒**；
- H1 的 statement 直接写着 **"达到 45 pass、0 fail"**——答案在假设里；
- `prereg/P1.json` 的频段是 **`[45, 45]`**。**离散未知量上的零宽频段是一份自白。**
  没有人会在观测前把一个整数预测成点区间。

**判断**：`research-mcp` 以 journal 为唯一真相，但 Agent 手上有两条**不留痕**的同源观测渠道——
`Bash` 与 `ipython`。预登记只有在**观测被垄断**时才有意义，当前没有。违规事件从不进入账本，
C4 结构性不可见。这一场因此是**流程测试，不是证据测试**：管道跑通了，认识论没跑。

**修法**（两条，可叠加）：

- **结构性**：研究战役跑在**禁用 `Bash`** 的会话里，使执行渠道只剩 `probe_run`（入账）与
  `ipython`（经 `research_kit` 只读）。这条才真正成立。
- **廉价检测器**：`prereg_write` 对退化频段（`lo == hi`）拒绝或高声告警。挡不住蓄意者，
  但正好挡住这次这种——而且它是 ARFT 意义上"模型不拥有的类型检查器"。

### 2.2 子代理继承可写的 research MCP，无任务级工具收敛

**实证**：`grill-adversary` 自行创建了旁路战役 `packages-research-mcp-tests/`——
`run.init` 08:47:25 → 两次 `prereg.write` → 两次 `probe.start/land`（均 exit 1）→ 六条 `attack.record`，
全程 08:47:25–08:49:30。正确战役未被篡改，但这是运气不是隔离。

**注意一处纠正**：起初怀疑成因是 `agent-permission-service.ts:135` 的
`if (options.agentID) return allow()`（子代理调用自动批准）。**不是**——该函数在生产中
根本不可达（§5.1）。真实成因更简单：**没有任何按子代理收敛工具面的机制**，
子代理直接继承父代理全套工具，包括可写 MCP 与 kernel。

**为什么在本前提下是阻断项**：C1（journal 唯一写者）与 C3（kernel 只读）同时被穿透，
而没有权限询问作为最后一道。一个对抗子代理能初始化战役、预登记、执行探针、落攻击——
它本该只能读一份不对称视图然后写一个文件。

**修法**：给对抗子代理一份**只读 MCP 视图**（或按任务限定的工具 allowlist）。
`claim_view` 已经把"该看什么"定义清楚了，缺的是把"能做什么"一起收敛。

### 2.3 `rlm()` 扇入契约与运行时不符，攻击回收靠翻捡

**实证**：父侧 `handle.session_dir` 为 `.../sub-489fc4d7`，子侧 `RLM_SESSION_DIR` 却指向
**父级 artifact 目录**。P4.2 写进 `research-grill/SKILL.md` 的
`Path(os.environ['RLM_SESSION_DIR']) / 'attacks.md'` 因此落错位置。

回收之所以看起来成功，是父代理去翻了日志和上级路径：父侧 G1/G2/G3 与子侧 G1/G2/G6
**逐字相同**——是抄回来的，不是按契约扇入的。

**为什么是阻断项**：这是 P4.2 唯一的子代理协作通道，且 skill 文案与运行时**明确矛盾**。
一条写进 skill 却在运行时不成立的指令，属于已立案的
`impossible-instructions` 病种——看起来像模型不听话，实际是契约错的。

**修法**：先确定哪一侧是对的（Prime 的 `RLM_SESSION_DIR` 语义 vs Proma 的 handle），
然后**只改一侧**；两侧都留着描述不同事实是最坏结果。

## §3 重要但不阻断

**3.1 `plan` 模式会执行 shell 命令。**
`agent-orchestrator.ts` 的 `case 'plan'` 分支末尾有
`if (toolName.startsWith('mcp__')) return allow`，`mcp__*__probe_run` 命中。
于是：`ipython` 被拒（不在 `PLAN_MODE_ALLOWED_TOOLS`，`:1142-1147`），写 Bash 被拒，
但一个 spawn bwrap 子进程执行冻结命令、并向 journal 追加事件的 MCP 工具被放行。
该 blanket allow 写于"MCP 即调研查询"的年代；research MCP 是**写+执行**面，必须从该分支拆出。
按 §0 前提降级为不阻断——但 UI 仍提供该模式。

**3.2 H2 是 ¬H1，不是竞争假设。**
H1 = "pass=45 且 fail=0"，H2 = "pass≤44 或 fail≥1"。一个假设和它的补集是**一个**假设——
ARFT 的 F4（单例假设空间）换了件衣服。`disjoint_pairs` 尽职地返回了一对，
让假设空间**看起来**可判别，实际判别性是恒真的。
`research-abduce` 缺一条规则：按取反划分同一条轴的两个 claim 不计作两个。

**3.3 `research-kit` 未被安装，只读保证名不副实。**
首次 `import research_kit` 抛 `ModuleNotFoundError`，多次 `uv pip install` 失败后
靠手工加 `sys.path` 完成使用。P4.2 的核心论断——"Python-backed skill，kernel 启动时导入，
被所有 `rlm()` 子代理继承"——**当前不成立**，它是靠绕过工作的。
C3 因此不是"结构上不可写"，只是"这次没写"。

**3.4 run 根目录跟随 MCP 进程 cwd。**
`server.ts:47` `PROMA_RESEARCH_CWD ?? process.cwd()` → `state.ts:133`
`resolve(cwd, '.proma-research', run)`。战役因此落在 `apps/electron/.proma-research/`
而非会话工作区。逃生口存在但**不是按会话的**，也不在 UI 中可见——用户无法在发起前确认落点。

**3.5 provenance 不记录沙箱证据。**
`probes/P1/provenance.json` 有 command / exitCode / 起止时间，没有"是否经 bwrap、bwrap 路径"。
审计者读产物无法区分沙箱执行与宿主执行（本次靠复算旁证，见 §1.2）。补一个字段即可。

## §5 测试覆盖里的虚假信心

45 + 15 全绿、7 个工作区 typecheck 退出码 0，这些数字**对 §2.1 一无所知**。三处具体的信心错配：

**5.1 `pi-ipython-permission.test.ts` 证明的是包装层遵守裁决，不是生产会产生裁决。**
三个用例全部直接注入 `canUseTool` stub。生产中该分支不可达：`bypassPermissions` 在到达询问前
已返回 `allow`。更关键的是——`agent-permission-service.ts:120` 的 `createCanUseTool`
（构造询问、维护白名单、管理 `pendingPermissions` 的那一整套）在全仓库中**只被它自己的测试文件引用**。
生产里唯一活着的询问入口是 `requestSingleApproval`，只服务三个 planning 删除工具。
按 §0 前提这不算缺陷，但**机件必须删除或显式标注为 dead**，否则测试名会持续宣称一道不存在的控制。

**5.2 一个用例的名字与断言方向相反。**
`pi-ipython-permission.test.ts:42` 名为
`反向：权限回调缺失（如空闲期）→ 默认拒绝而不是放行`，
函数体断言 `expect(calls).toHaveLength(1)`——即**执行了**。行内注释解释了该语义是有意的直通，
但扫测试名的人读到的是 fail-closed，拿到的是 fail-open。**改名，不改断言。**

**5.3 现有套件在结构上无法覆盖 §2.1。**
所有 45 个用例都作用于 journal 内容；失效模式是**一个永远不进 journal 的事件**。
这不是加测试能补的洞——只能靠收敛工具面（§2.1 结构性修法）或加退化频段检测器。

### 修复过程中被自己的测试抓到的一个缺陷

`collect_attacks` 最初会向上找父目录。反向用例（"子代理还没写完 → 返回空"）在 `tempfile.mkdtemp()`
上跑时收到了真实攻击行——因为 `/tmp` 就是父目录，而 P4.3 那次子代理正好把 `attacks.md` 写在
`/tmp`。越界会把无关战役的攻击收进证据链。已改为只扫会话目录与其 `sub-*` 子目录。
（这也是 `RLM_SESSION_DIR` 根因的发现路径——比读源码更快。）

### 仍未修、且必须由人决定的

1. **禁用 Bash 的研究会话**（§2.1 的结构性版本）。零宽频段拒绝挡住了最常见的那次，
   但只要 Agent 手上还有 Bash 与 kernel 两条不留痕的观测渠道，预登记就仍是**执行顺序纪律**
   而非结构保证。做成硬模式要动 Proma 的会话工具面——属于产品决策，等你拍板。
2. **`agentID` 是否在 rlm 子代理调用上被填充**，未经实测。钉死战役名不依赖它，
   但更细的按子代理工具收敛依赖它——下一场 UI 战役顺带验一次即可。
3. **`apps/electron/package.json` / `bun.lock` 里新增的 `@earendil-works/pi-tui` 依赖**
   （非本次改动，工作树里已存在）使 `planning-manager.test.ts` 失败：`node_modules/electron`
   未安装，`electronBinary` 解析成对象而非路径。已用 `git stash` 二分确认**与本次修复无关**，
   单独回退这两个文件后该用例即通过。需要一次 `bun install`（会下载 Electron 二进制）——
   属于环境/依赖决策，未擅自执行。

## §8 赛事口径下的下一步（`Race/` 为权威，截止 2026-09-05）

审计范围之外、但模板结构性要求的三项缺口——**这才是现在的主线**：

1. **两轮闭环是硬性结构**。模板 P14（第一轮计划）/ P16（调整依据）/ P17（第二轮）
   要求第二轮的计划**由第一轮的真实结果导致**，且 P11 明写"重新生成一次方案本身
   不等于反馈迭代"。P4.3 只跑了**一个探针、一轮**——现有 `claim_transition → 下一个探针`
   已经是真反馈机制，缺的是把它跑满两轮并留档。
2. **至少一组同条件对照**（P18）。同 world / 同 seed / 同预算。
3. **评委可直接体验的服务**（P20 + 答疑 Q13：初赛评估期内必须保持可用）+ 百炼 Qwen 调用凭证。

建议次序：先按新护栏跑一场**两轮**战役（护栏会强制频段有宽度、强制第二条假设是
另一个机制），产物直接填 P13–P17；再补 P18 对照；最后做前端/API 与报告。
